# Stand up a new workspace

## Use when

Use this procedure when a coherent area of work has no usable workspace entry point.
It may live in a repository, document system, shared folder, application, or a combination of systems.

Do not use it merely because a new folder or project exists. For one-off work with adequate existing routes,
perform the task and retain decisions in the ordinary work record. If an existing workspace is close, use
[Adapt an existing workspace](adapt-existing.md). This is builder guidance, not a
procedure that every resulting workspace must adopt.

## Start with

1. Use [Workspace discovery](../discovery.md) with the requester. Ask only questions
   whose answers could change the design or first useful task; record explicit
   assumptions for the rest.
2. Identify one representative task from ordinary work that is safe to execute with
   the authority already available.
3. Read the applicable instructions in each host and the
   [workspace core rules](../../agentic-workspace/04-conventions-and-rules.md).
4. Choose the existing conversation, issue, or task record that will retain setup
   decisions, assumptions, trial outcome, and unresolved gaps.

Treat requester answers as claims to verify where practical. A named source or tool may be
unavailable, stale, or useful for a narrower purpose than expected.

## Actions

### 1. Set the boundary and host

Before choosing a layout, trace the representative task through the information
it needs, source authority and freshness, actor capabilities and access, actions,
handoffs, outputs, checks, and activity or audit record. Use that evidence to
choose the workspace boundary, host, and minimum useful organization.

Write a one- or two-sentence purpose and significant exclusions. Keep one workspace while work shares a
coherent purpose and similar context routes. Split it only when different purposes or access boundaries make one entry point misleading.

Choose the host actors already use. Do not introduce a repository, portal, or folder hierarchy solely
for completeness. A workspace can link to sources in other systems without copying them.

### 2. Draft the shared entry content

Create or update one concise entry document or landing page that answers:

- what the workspace is for and outside its scope;
- where to look for common questions or tasks;
- which capabilities are available and how to use them;
- how a human or agent starts work;
- where ongoing work and final outputs belong; and
- which real constraints, gaps, or escalation routes matter.

Link to designated sources instead of restating them. Route by question or task and
say why each source is relevant. Distinguish facts, defaults, constraints, drafts,
examples, and historical rationale.

When defaults can vary, state the resolution route. The usual order is shared
defaults, workspace defaults, selected procedure or workflow defaults, then task
choices. A task choice does not remove a constraint or grant access. For a small
workspace, this entry content can be the entire implementation.

### 3. Connect actual entry mechanisms

Expose the shared entry content where each intended actor really starts: a repository
README for humans, the instruction file an agent runtime actually loads, a shared
folder or document-system landing page, or an application's relevant home or help
view. Keep runtime-specific entry files thin and point them to the same content.

Confirm each in-scope human and agent route works. Directory nesting alone does not establish instruction inheritance.

### 4. Make context routes credible

For each route needed by the representative task, state the question it answers,
when to consult it, its source location and access method, what it is authoritative
for, and whether it holds current facts, intended behavior, background, or examples.

Preserve source links for material claims. When sources disagree, record the specific
disagreement and seek an authoritative record or observation. Do not treat factual
disagreement as an instruction-precedence problem.

If access is unavailable, identify the affected actor and dependency. Do not copy restricted or changing
content merely to make a route appear usable.

### 5. Verify available capabilities

Check that intended actors can actually reach and use the people, skills, tools,
services, or scripts needed for the task. Record the practical invocation route when
it is not obvious. Tool presence alone proves neither access nor authority.

Use an available alternative when it serves the outcome. Otherwise disclose the missing capability and the
work it prevents. Add no capability registry or install requirement unless ongoing work demonstrates its value.

### 6. Add only justified work guidance

Describe how an ordinary request starts and where its result goes. Add a reusable
procedure only when repetition or complexity makes written instructions useful, and
a workflow only when explicit connections or handoffs improve delivery. Use
[Author guidance](author-guidance.md) when writing either form.

Keep reusable how-to guidance separate from a run and its outputs. Retain run-specific
scope, assumptions, decisions, result links, and checks in the existing conversation,
issue, or task. Do not create universal run folders, IDs, templates, or status systems.

When useful, adapt this small drafting aid rather than creating a standalone template:

- **Purpose:** what belongs here and what does not.
- **Start work:** request path, output destination, and important constraints.
- **Find context:** task-oriented links with authority and freshness notes.
- **Use capabilities:** available means and their invocation or access routes.

Adapt or omit headings for the host; do not publish empty sections.
### 7. Exercise one representative task

Start from each relevant entry mechanism as a new actor would. Follow only the routes
the task needs. Confirm the actor can establish outcome and scope, find material
context, distinguish source roles, invoke capabilities, choose an output destination,
and identify a proportionate check.

For work under a ticket, confirm that its ordinary work record can capture who
or what acted and when, actions and capabilities used, systems or artifacts
inspected or changed, affected resources and resulting state, outcomes, handoffs,
and evidence; link detailed system audit records when local requirements call
for them. Also confirm that a verified change can be reflected in its
authoritative source, or that a discrepancy can be surfaced when it cannot.
Confirm the durable task record can preserve the goal, decisions, completed
actions and evidence, next action, and any pending or uncertain external action.

Execute the task when authorized and useful. Otherwise walk through the proposed
actions and label the trial as a walkthrough. Fix misleading routes and small gaps.
Record access, authority, capability, or domain gaps that prevent a credible trial;
workspace structure does not solve them.

Use stated assumptions for routine, reversible setup choices. Ask the requester only
when an unresolved choice materially changes the boundary, authority, destination,
or useful result.

## Result

The result is the smallest usable workspace in its chosen hosts, with one discoverable shared entry point
and working routes to context, capabilities, work, and results. The
setup conversation, issue, or task contains material decisions, explicit assumptions,
the representative task, trial result, and remaining limitations.

## Check

The workspace is ready when an intended human or agent can start at its real entry
mechanism and complete, or credibly walk through, the representative task without
unrelated reading or invented facts. Verify routes exist, required capabilities are
available to that actor, output and check are clear, and source authority and gaps
remain visible. For work under a ticket, verify the existing work record can
retain an activity and change audit trail and point to supporting evidence.
Confirm documentation has a route for updates based on verified reality and
durable learning has an appropriate home. Verify a fresh actor can resume from
the durable record, inspect current external state, and resolve a pending or
uncertain action before deciding whether to retry it.

Report the entry point, hosts, task exercised, execution or walkthrough status, check outcome, and access,
authority, capability, or domain gaps. Empty scaffolding and unverified links do not satisfy this check.
